## Delivery

An owner request includes implementation, appropriate checks, review, merge, established production deployment and live verification. Continue without a second routine go-live instruction. Do not require model, reasoning, quota or tool-mode selection. Use available tools; report precise access blockers and continue independent work.

- Copy, styling, navigation and compatible interface changes: focused tests and affected-page verification. No private deployment, credential exercise or launch acceptance is required unless affected.
- Functionality/backend changes: focused regression and relevant compatibility/security checks. Use existing hosted CI; a cloud checkout is valid when the GMKtec is unavailable.
- Authentication, private data, spending, public contribution publication, CoL meaning/data or destructive changes: preserve the affected subsystem's stronger controls. A code release does not authorise a new content disclosure or a higher spending ceiling.
- Reuse established qualifications until a relevant change, expiry, revocation, incident or contradictory evidence invalidates them. Do not repeat initial consent registration, activation, cursor setup, key rotation, complete private-source reconciliation or recovery qualification for unrelated updates.
- Review the diff and successful applicable CI before merging. Report observed deployment and live results, distinguishing source shipped from private capabilities enabled. Never invent acceptance or publish diagnostic club content.

`node scripts/local-dev.mjs check` runs the offline Python/Node suite; `preview` serves loopback only. Browser fixtures run in hosted CI for affected rendering. Physical-device/screen-reader checks and new test-only member contributions are post-launch follow-up, not routine release prerequisites.
