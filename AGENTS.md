## Standing simplicity instruction — 21 October 2026

Stammtisch is a website for six friends, not a regulatory institution. **Remove avoidable barriers across the entire website.** Prefer a clear page edit and an existing workflow to another form, account, approval, document-recovery exercise, service, ceremony or release ritual. If a real member rule is clear, interpret it and publish the Club's current plain-language rules without waiting for another vote, the old Google document or unrelated evidence that cannot change the meaning. The Club may correct an imperfect interpretation later.

Keep the distinction small and truthful: **the Club's publicly adopted words can be updated immediately; recorded points, private rights, automated score changes and sealed historical rules must not be silently altered or falsely certified.** Implement score-sensitive calculations separately with focused testing and the existing protected checks; uncertainty affecting one calculation holds that case, not an otherwise safe rulebook edit. Never use a technical blocker as a reason to describe an already-settled Club question as an unresolved Matter for Club Deliberation.

Public-facing Matters for Club Deliberation use the existing Stammtisch editorial voice: one or two short, wry sentences identifying a *genuine outstanding Club decision*, without internal terms such as non-operative, snapshot, ledger, Viewer, qualification or release gate. Keep technical evidence in current-state.md / Issue #24 rather than in the rulebook.

## Delivery

An owner request includes implementation, appropriate checks, review, merge, established production deployment and live verification. Continue without a second routine go-live instruction. Do not require model, reasoning, quota or tool-mode selection. Use available tools; report precise access blockers and continue independent work.

- Copy, styling, navigation and compatible interface changes: focused tests and affected-page verification. No private deployment, credential exercise or launch acceptance is required unless affected.
- Functionality/backend changes: focused regression and relevant compatibility/security checks. Use existing hosted CI; a cloud checkout is valid when the GMKtec is unavailable.
- Authentication, private data, spending, public contribution publication, CoL meaning/data or destructive changes: preserve the affected subsystem's stronger controls. A code release does not authorise a new content disclosure or a higher spending ceiling.
- Reuse established qualifications until a relevant change, expiry, revocation, incident or contradictory evidence invalidates them. Do not repeat initial consent registration, activation, cursor setup, key rotation, complete private-source reconciliation or recovery qualification for unrelated updates.
- Review the diff and successful applicable CI before merging. Report observed deployment and live results, distinguishing source shipped from private capabilities enabled. Never invent acceptance or publish diagnostic club content.

`node scripts/local-dev.mjs check` runs the offline Python/Node suite; `preview` serves loopback only. Browser fixtures run in hosted CI for affected rendering. Physical-device/screen-reader checks and new test-only member contributions are post-launch follow-up, not routine release prerequisites.

## Boundaries

The repository, branches, PRs, issues, logs and Pages are public. Keep raw email, private originals, contacts, exact private logistics, consent proofs, credentials, workbook exports and subscriber data private. Use only approved, screened derivatives and existing scoped, revocable permissions. Do not infer rights from an allowlist or an AI output.

Keep the existing owner-only Apps Script project/deployment and single 15-minute HEAD trigger. Preserve its private manifest, settings, journals, one-shot state, ledger, cursors and original receipt boundaries. Saving HEAD changes scheduled execution immediately; the web app needs an in-place version update. Follow the runbook only when private code changes.

Keep CoL independent verification, signed awarded allocations, replay protection, historical results and new-confirmed-passing-only push delivery. The Club has settled the Renewal-to-Renewal interpretation; the precise first-2027-gathering cutoff is a **future fact not yet recorded**. Do not assume its clock time or rewrite earlier scores. One authenticated member may initiate clear prospective CoL wording changes without an extra vote/owner-adoption gate. For score-affecting implementation, use the existing qualified safeguards only for the affected behaviour; hold missing evidence for that case rather than invent it.

Owner direction, 18 October 2026: GMKtec-first is the default for ordinary development, offline Python/Node checks, previews and testing; do not use cloud development machines or agents for tasks the owner-local checkout can perform. Keep production, scheduled monitors, Pages and independent PR CI on **GitHub-hosted runners**: this public repository is unsafe for personal self-hosted runners, and its standard hosted Actions minutes are free. Never attach the GMKtec, Comparative, LCRS or thefish as a public repository runner or share credentials/services. Explicitly identify exceptions when local execution was unavailable, without claiming work was done locally. Do not add paid services or expand permissions without the required authority. Financial ceilings remain operative. The already-deployed private Apps Script version retains its dates until an authenticated in-place update; publisher credentials must continue to expire on their independently verified actual date.

## Keep it small

Update the single current-state record when state actually changes; use Issue #24 for evidence and actionable remaining work. Do not prepend competing status bulletins to instructions. Before adding a service, gate or recurring check, explain its concrete benefit, simpler alternative, upkeep and exit condition in the change description.
