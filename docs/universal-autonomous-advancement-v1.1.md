# Universal Autonomous Advancement — Execution Mode and Usage Controls v1.1

Owner-approved for repository recording on 8 October 2026. The policy below records the owner's supplied v1.1; repository integration notes follow it.

## Mandatory launch question

Before starting a new on-demand advancement window, ask:

Which execution mode would you like to use?

1. ChatGPT only — Use regular ChatGPT and its available tools. Do not invoke Work or Codex.
2. ChatGPT + Work — Allow Work for authorized execution, strictly restricted to the lowest approved usage configuration. Do not invoke Codex.
3. ChatGPT + Work + Codex — Allow both Work and Codex, strictly restricted to the lowest approved usage configuration.

Default: Mode 1 — ChatGPT only.

Do not activate a higher mode without my explicit selection.

If I specify the mode in my launch instructions, proceed without asking again.

## Scheduled execution

When establishing a recurring schedule, ask me to select the execution mode once.

Save the mode in the project’s durable configuration and apply it to every scheduled continuation within that series.

Do not ask again every hour.

Do not automatically expand the mode on subsequent runs, even if additional tools would make the task easier.

Any change from ChatGPT-only to Work, or from Work to Codex, requires my explicit authorization.

## Mandatory Work and Codex configuration

Whenever Work or Codex is authorized:

* Preferred model: GPT-6 Luna.
* Reasoning effort: Low.
* Speed: Standard.
* Fast and Ultrafast: Prohibited.
* Automatic escalation to stronger models: Prohibited.
* Additional credit purchases or paid resets: Prohibited.
* Automatic credit reload: Must remain disabled where the account provides this control.
* Parallel agentic execution: Prohibited unless independently authorized.
* External paid services: Subject to existing project-specific approval and budget limits.

Only use a service after its actual model, effort and speed settings have been verified through available product controls.

Writing these instructions does not change product-level model settings.

If the required low-usage configuration cannot be verified or is unavailable, do not launch that service. Explain the limitation and request authorization for any alternative.

Never silently substitute a more expensive model.

## Usage protection

Work and Codex may share a usage allowance and purchased-credit balance.

Before beginning a substantial agentic run, check the remaining allowance when the product provides that information.

Do not assume an 8-hour window corresponds to eight hours of affordable or available model execution.

Minimize unnecessary model calls, repeated research, duplicated repository scans, redundant context loading and speculative implementation.

Reuse durable project evidence and previous results.

Prefer focused, well-specified tasks rather than repeated broad autonomous investigations when a lower-cost approach achieves the same objective.

Use one active Work/Codex worker at a time by default.

Stop launching new agentic jobs if available usage information indicates that the approved allowance is exhausted or the approved usage boundary may be exceeded.

Do not knowingly consume purchased credits unless I have separately authorized their use.

If actual consumption cannot be measured or controlled adequately, disclose that limitation and avoid launching open-ended agentic work.

Never claim that a prompt-level limit is a technically enforced billing limit.

## Quality protection

Low usage does not justify lower standards of evidence, safety or validation.

If a task requires reasoning or technical capability beyond the authorized model configuration:

1. Stop that specific task at a recoverable boundary.
2. Preserve the evidence and current state.
3. Record why the lower-usage model is insufficient.
4. Identify what stronger analysis or execution would be needed.
5. Continue with another eligible task that fits the authorized mode.

Do not independently increase the model or reasoning level.

Do not bypass safeguards to complete work cheaply.

## Continuous operation

Within the selected mode, follow the existing advancement cycle:

ZOOM OUT → PRIORITIZE → EXECUTE → VERIFY → RECORD → REPEAT.

Complete as much meaningful authorized work as practical.

The selected execution mode is a ceiling, not an instruction to use every available tool.

A task should use the least resource-intensive method capable of meeting the required quality and evidence standards.

The hourly recovery system must preserve the selected mode and all usage safeguards.

## End-of-window usage report

Include a concise usage section in the consolidated final report:

* Authorized execution mode.
* Actual Work and Codex models used, where verifiable.
* Reasoning effort and speed, where verifiable.
* Work and Codex allowance consumed, if available.
* Purchased credits consumed, if any and verifiable.
* Any usage-limit or verification failures.
* Whether the next window can safely proceed using the same configuration.

Clearly distinguish measured usage from estimates or unavailable information.

Overall rule: Maximize meaningful progress within the explicitly selected execution mode and approved usage limits. Never maximize activity at the expense of usage efficiency, safety or quality.

## Repository integration and activation status

- **Recorded policy, not an active window or scheduler.** Adding this file does not start an eight-hour run, create hourly recovery, select a scheduled execution mode, alter product settings, or verify model availability, speed, allowance or billing controls. A launch request and any required configuration verification remain necessary.
- **Scope and precedence.** For advancement windows governed by v1.1, these owner-approved execution-mode and usage limits constrain older general routing/delegation guidance. Older model maps, everyday-setting preferences, standing delegation permission or quality-escalation rules do not authorise a stronger model, extra worker, different service or spending beyond this policy. If required quality exceeds the allowed configuration, preserve the task and seek explicit authority for the alternative. Existing project authority, source rights, privacy, semantic review, attempt limits, active-work guards and budgets still apply.
- **No new project authority.** An execution-mode selection permits only the selected execution surfaces within otherwise authorised work. It does not approve a new phase, source, external provider/use, publication, sensitive disclosure, cloud workload, paid service or retry of consumed evidence. Existing merge/publication rules remain applicable.
- **Durable recovery.** When a window or schedule is separately established, record its project, window/series identifier, explicit selected mode and authorisation, scope, start/end boundary, verified settings and verification time, usage availability, current task, completed evidence, blockers and next eligible action in the project's existing approved handoff/configuration location. Preserve the selected mode and controls on recovery; a missing mode is not permission to expand execution. Do not place private account details or credentials in a public repository.
- **Product controls remain external.** A file, prompt, model name or tool description is not evidence that the actual product configuration or billing boundary is enforced. Recheck through available product controls before using Work or Codex. Do not describe an unverified configuration as compliant.
- **Independent project copies.** The same v1.1 policy is being recorded separately for Stammtisch, LCRS and Comparative at the owner's request. Each repository retains its own substantive governance. Later policy revisions require deliberate reconciliation; the repositories do not automatically synchronise.
