## Exactly what this implementation can qualify

unchanged words, numbers, punctuation, paragraph boundaries, headings,
qualifications and exceptions. Only horizontal spacing, nonbreaking spaces and
straight/curly typography of an existing apostrophe may differ. The authenticated
member supplies both complete literal passages in the instruction
`In the CoL rules, replace "..." with "...".` The complete message body must match
that instruction. Its subject needs no tag. The model must also have classified
the fresh request as operative. A fixed server-written explanation prevents
model-invented public explanatory claims.

The additional `editorial-rewrite-v1` class accepts a complete, authenticated member-authored replacement in ordinary language. It only stages a release when all affected sections are mechanically equivalent after whitespace/apostrophe normalisation, the actual replacement passages occur in the original source, and hosted verification independently checks every section. It cannot treat AI interpretation or a model confidence assertion as authority for changed meaning. Any changed points, penalties, draft benefits, payouts, qualifications or retrospective effects remain non-operative until matching verified behaviour is available.

This recognized form is an automatic implementation class, not a requirement that
members use a form or command. Other natural prose still receives interpretation

## Two stages and their independently checked phases

1. **Stage a non-operative candidate.** A domain-separated signed envelope binds
   the exact current ledger, public five-file baseline, authenticated sanitized
   revision, implementation commit and behavior digest. A GitHub-hosted job
   independently observes the authoritative Sheet through the existing Viewer
   identity. Submitted source proof or a mutable repository variable cannot
   replace that read. The immutable candidate is
   `data/col-releases/<candidate-digest>.json`. It contains complete public-safe
   narrative, official Markdown, version catalog, register JSON and register HTML
   with individual byte hashes. Its new version is `verified:false`;
   `publishedAt` and `effectiveAt` are null.
2. **Authenticate activation separately.** The private script independently reads
   the hosted candidate and exact current base, then signs a distinct
   source/base/candidate-bound activation message. The hosted job rereads the
   Viewer source and checks unchanged behavior and base before writing immutable
   `-activation.json`, whose operative dates are still null. A later private
   readback of the hosted candidate and activation intent authorizes the third,
   separately signed confirmation message. Its hosted job checks source, base and
   behavior again and writes the complete immutable `-confirmed.json` ready
   snapshot and a `release_pending` ledger entry. This snapshot still has no
   operative timestamp and is not active merely because it exists.

The confirmation job then requests Pages publication and independently verifies
exact hosted bytes for the ledger, candidate, activation and ready snapshot. Its
next mandatory step performs another independent Viewer read and requires the
same source digest. **Only successful completion of the entire job establishes
the publication clock.** A failed, skipped, running, late or unverifiable job
leaves the previous complete version operative.

After independently verifying that job and all hosted packages, the private
script signs a fourth message to retain the completion evidence. The hosted
retention job independently verifies the same public job metadata again, then
writes immutable `-witness.json` and its digest into the ledger. Retention does
not activate a version or change its clock. It stores evidence of an already
completed release, allowing history to survive job API expiry, deletion or rate
limits. No later Sheet read is used to rewrite this past observation.

Final private readback requires the exact hosted retained receipt as well as the
complete release before completing the private request and sending success. The
normal 15-minute intake trigger reconciles the global pending CoL operation
before its bounded folder walk; no new trigger is installed. Activation has a
45-minute lease, while signed messages and phase source observations have
five-minute acceptance bounds. These are machine verification phases, not extra
human policy approvals.

## The publication clock and permanent record

`submittedAt` comes from the authenticated private source. `stagedAt`,
`authorizedAt`, `candidateObservedAt` and confirmation `observedAt` are evidence of
intermediate checks. None is publication or operative effect.

The ready snapshot records the trusted runner's repository, workflow path, job
name, run ID, run attempt, workflow head SHA and checked-out implementation SHA.
The reader and private script independently use public, fixed-repository API
routes for that **specific attempt**:

- `/actions/runs/<run-id>/attempts/<attempt>`
- `/actions/runs/<run-id>/attempts/<attempt>/jobs?per_page=100`

They check the repository, `repository_dispatch` event, workflow path, run ID,
attempt, workflow head SHA, unique job identity and completed successful run/job.
They also require successful mandatory steps named `Verify complete hosted ready
snapshot` and `Verify final independent Viewer source`. Source checking must
start after hosted verification finishes. The job must complete after that source
step and within five minutes of the source step starting. A later rerun cannot replace the
original attempt's evidence. These are the documented GitHub
[workflow-run](https://docs.github.com/en/rest/actions/workflow-runs) and
[workflow-job](https://docs.github.com/en/rest/actions/workflow-jobs) APIs.

The successful job's `completed_at` supplies the projected `publishedAt`,
`effectiveAt` and `confirmedAt`. It must follow the private activation readback
and fall within the activation lease. These timestamps are never manufactured
from a dispatch, commit, Pages request, private signing time or early candidate
observation. The final private `verifiedAt` is later and records when complete
hosted release and retained evidence were independently read back. Displays use
America/Toronto.

The retained receipt binds the exact candidate, activation, ready-snapshot digest,
producer and original completed timestamp. It records its own later verification
time without shifting the operative date. Readers hash-check that receipt against
the ledger and verify its identities and clocks. Before retention is hosted they
use the pinned job API. If a new ledger reaches a cache before its receipt, the
same original live job proof remains an available fallback. Private success still
requires the retained receipt itself to be hosted.

Public readers trust the existing site's origin integrity; they do not receive a
private HMAC key or claim independently to authenticate a member. The receipt is
an immutable retained observation under that existing trust boundary, not a new
external certification service. Publication and source observation are not a
globally atomic transaction: a source can change after its last read, and CDN
edges can see releases at different times. The bounded class leaves executable
parameters and meaning unchanged. Wider semantic/financial/formula changes need
their own engineering and timing contract.

`ANNALS_RULES_V3_CLOCK_QUALIFIED` stays OFF pending genuine controlled hosted
acceptance of this precise protocol alongside the existing security and hosted
gates. Offline mocks do not provide that evidence.

## Supervised first-production acceptance

The source-bound acceptance lane closes the bootstrap dependency without asserting
hosted or clock qualification before a real release. It supports only the exact
`oldest-death-steal-v1` template against an empty v3 release ledger. It cannot
process another source, add an arbitrary amendment, reuse a consumed attempt or
automatically enable broader operation. Installing this code is not acceptance.

Before arming, complete genuine signing qualification and outstanding-record
reconciliation. The private desk's signing qualification action rechecks the
actual old-signature rejection and the fresh nonpublishing GitHub challenge. Its
immutable `verified_signing_only` record retains the historical withdrawal-receipt
gap and the operator's reconciliation provenance; it never invents the missing
receipt. Acceptance requires that record through
`ANNALS_SIGNING_QUALIFICATION_RECORD`, its matching actual verification timestamp
in `ANNALS_SIGNING_REMEDIATED_AT`, and affirmative genuine evidence. The hosted
`ANNALS_SIGNING_REMEDIATION_VERIFIED` variable must be set only after those real
checks. Neither acceptance preparation nor arming creates these markers.

After the reviewed source is merged and installed in the existing owner-only
deployment, the supervised sequence is:

1. Open the genuine unconsumed original in the private desk. **Prepare exact
   original acceptance** reads the preserved source, current consents, exact
   current hosted base and implementation. It makes no private write or dispatch.
2. After actual security and record reconciliation, explicitly arm that prepared
   binding. The server rereads it and refuses any intervening change. It reserves
   one immutable private record in the source folder and root, with a fixed
   45-minute deadline. A failed/partial reservation is retained, never reset or
   automatically extended. Arming sends no publishing request.
3. Configure repository variable `ANNALS_RULES_V3_ACCEPTANCE` to **only the
   returned descriptor object**, with no enclosing status object. Its exact schema
   includes a random nonce, sanitized public revision ID, exact stage-content and
   initial-ledger digests, reviewed implementation and behavior digest, arm time
   and expiry. Original source ID, email, excerpt and private source hash never
   belong in this variable or public logs. Leave V2/V3 broad release, hosted,
   clock and automatic-template flags false or absent. The runner independently
   rejects a malformed descriptor, wrong binding, another revision or open broad
   qualification flags; YAML admission alone grants no publication authority.
4. Use **Continue the authenticated oldest-death amendment** once. This retains
   the original receipt and false intake-eligibility value, adds its original
   continuation/request journals, and reserves the first signed stage. Do not
   resend the email. Any unknown dispatch result remains consumed.
5. Supervise **Check and advance the saved phase once** and read its saved status.
   The ordinary trigger retains its existing cadence. Both paths reconcile the
   same journal and may issue only the next unconsumed phase. Every phase retains
   the usual signature, source, exact-base, behavior, hosted-readback and job-clock
   checks. Do not merge another implementation during the window.
6. The activation lease is clipped to the original acceptance deadline. Expiry
   blocks new staging, authorization and confirmation. It does not prevent
   retaining evidence of an already completed timely release, final readback, or
   existing bounded exact-operation cancellation. Keep the descriptor until this
   terminal reconciliation finishes; deleting it earlier can hold hosted recovery.
   No attempt history is cleared and no deadline is renewed.
7. Only a complete timely production release, retained hosted witness and final
   private `verified_live` state constitute successful acceptance. Preserve the
   reservation and audit records. Remove the hosted acceptance variable after
   terminal reconciliation. Qualification of broad automatic operation remains a
   separate evidence-based action; this lane never sets those flags itself.

The hosted workflow still uses its existing GitHub-hosted runner, publication
concurrency, compare-and-swap push, independent Viewer identity and final source
observation. No account, permission, trigger, AI call, workbook write, spending
allowance or notification channel is added. Publication time remains the verified
original completion clock, never the arm or dispatch time. Both clock verifiers
accept only the fixed workflow's bare path or that exact path with `@main`.

## Future dates and source-dependent changes

The stage reducer can retain an explicit future timestamp without activation.
Time alone never grants activation. Due-time authorization checks the exact
current base, source and implementation; an intervening revision cannot be
overwritten. A missed exact effective time is refused, never backdated or silently
moved. The private automatic typography adapter therefore holds **all explicit
scheduled timestamps** for engineering and, if necessary, one focused date
clarification. This is an unsupported automatic class, not a claim that
unattended scheduled activation works.

The Sheet remains authoritative. `observe-col-source.py` produces only a sanitized
digest/time/commit/workflow receipt of the independently observed semantic
workbook snapshot. Each observation binds its actual checkout commit. It does
not assess a proposed formula or allocation. The existing manual Editor route
and independent Viewer route remain the route for genuine source-dependent
engineering; no access expansion or Sheet write is implemented. Source
disagreement at any activation check, including the final post-hosting read,
holds the release.

## Failure, bounded recovery and history

The public ledger is `data/col-rules-release-state.json`. Phase events append
evidence digests and actual timestamps. Immutable candidate, activation, ready
snapshot and completion receipt files are never overwritten. All publication
jobs share the existing publication concurrency group and use a non-force Git
compare-and-swap push. A competing base, changed source/code, failed Pages build,
stale cache, missing file, bad clock or readback discrepancy does not establish
success. Unknown dispatch responses are reconciled read-only; an original
dispatch reservation is never cleared or automatically repeated.

`annalsCancelStagedRule` is an authenticated action bound to the original staging
authority and current ledger. Its reasons are limited to expiry, deployment
failure, withdrawal or source change. It can append a tombstone when an uncertain
stage never became visible: that changed ledger invalidates the delayed old
signature. It can cancel a failed or expired final job only after independently
checking that outcome. A successfully operative or sealed version cannot be
cancelled as a rollback. Cancellation is independently hosted and read back before
releasing the pending slot for a new revision identity.

If an in-flight stage wins a race with cancellation, the cancellation's old base
is stale. After its five-minute signature expires, a fresh authenticated owner
action can reserve one different cancellation attempt bound to the changed
append-only ledger. An unchanged base cannot be retried. Both full signed
envelopes and both dispatch markers remain in private history; two total
cancellation attempts exhaust the bounded recovery allowance.

If retention did not commit, `annalsRetainRuleWitness` permits one explicit
owner-authenticated recovery after the first signature expires. It must preserve
the exact original candidate, producer, ready-snapshot digest and completed time.
It uses a separate private journal identity and retains the first signed envelope.
An old in-flight job may race the recovery; immutable receipt creation and Git
compare-and-swap admit one receipt, and reconciliation accepts either matching
winning attempt. Two total retention dispatches exhaust the allowance. A second
failure remains an explicit engineering hold; no retries or attempt resets are
hidden. This recovery stores past evidence and cannot enact a new rule.

Serialized ledger and immutable packages are capped at 1 MiB UTF-8, below the
narrowest reader bound; each embedded file is capped at 512 KiB. Staging reserves
16 KiB of ledger headroom and phase-event capacity for completion, retention or
cancellation. Every reducer validates its returned ledger before writing. Capacity
exhaustion holds new work while preserving the current readable version.

## Complete readers and subsequent releases

`col-rules-reader.mjs` verifies the immutable candidate, activation and complete
ready snapshot, individual file hashes, source/clock bindings, version identity,
unchanged parameters and January state, then requires a completed job witness or
its retained receipt. A missing or mixed deployment falls back to the latest
complete predecessor. A supplied verified session snapshot cannot be rolled back
by a stale ledger. This is local admission of a complete version, not synchronized
switching at every network edge.

For the next release, Node and Apps Script bind the same **raw immutable ready
snapshot bytes** as the exact baseline. They separately use its verified retained
publication clock to select the structured current version. Node materializes the
prior active register/catalog internally before adding the next candidate. This
avoids requiring Apps Script to reproduce the Node HTML renderer byte for byte
and preserves prior dates and history. Tests exercise two successive complete
releases with the first release's live job API unavailable.

The Celebration page, revision register and version reader use the complete
snapshot. Stable official-reference links use
`col-rules-version.html?version=<revision-id>&reference=1` and show full Markdown
for that exact version. Static root files remain the dated baseline and safe
no-script/network-failure reference. They are never relabelled as a new revision.
No real candidate exists in this release, and original official rule words remain
unchanged.

## Gates and acceptance boundary

Private gates: existing rules readiness plus `ANNALS_RULES_V3_ENABLED`,
`ANNALS_RULES_V3_HOSTED_ACCEPTED`, `ANNALS_RULES_V3_CLOCK_QUALIFIED`; automatic
initial typography staging also requires `ANNALS_RULES_V3_AUTO_LITERAL_ENABLED`.
The literal qualification flag also guards owner-only manual typography staging; shared protocol readiness alone does not open an unqualified class.
The independent oldest-death template additionally requires the private
`ANNALS_RULES_V3_AUTO_OLDEST_ENABLED` gate (default false/unset); it must not
be enabled before complete signing and genuine hosted acceptance. Hosted gates:
`ANNALS_RULES_V3_RELEASE_ENABLED`, `ANNALS_RULES_V3_HOSTED_ACCEPTED`,
`ANNALS_RULES_V3_CLOCK_QUALIFIED`, and the existing independently verified signing
remediation gate. Missing means false. No property, variable, key or remediation
marker is changed by this implementation.

Private functions remain in `RulesProduction.gs`; no scope, account or trigger is
added. `annalsReadStagedRuleGates` returns configuration booleans only, without
reading signing/remediation markers or keys. `annalsStageLiteralRule` supports an
existing authenticated desk continuation. Cancellation and receipt recovery are
also authenticated desk actions. Network, signing and provider actions in these
files describe future qualified runtime behavior; they are not evidence that this
implementation task performed those actions.

Synthetic tests cover source grounding, failed/stale/mixed hosting, source/code/
base drift, concurrent updates, lost responses, bounded cancellation and retention
races, API expiry, rollback retention, byte bounds, explicit-date holds, permanent
version links, final source rechecks and actual Apps Script adapters feeding Node
reducers across simulated 15-minute intervals. Genuine installed-adapter, trusted
hosted clock, real Viewer and hosted failure/recovery acceptance remains external
work. All new gates remain off.
